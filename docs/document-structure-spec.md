# 문서 구조 공통 규격

> 모든 카테고리가 이 문서를 상속한다. 각 프로파일의 문서 골격 절은 이 문서를 참조하고,
> 카테고리 고유 블록만 남긴다.
>
> **1차 근거**: `data/raw/naver_official/` — 네이버 검색 공식 콘텐츠 가이드
> **계기**: 레시피 초안 v7에서 재료준비 블록이 글의 열두 번째 덩어리에 있었다.
> 검색해서 들어온 독자가 재료를 보려면 서론 4문단과 Q&A 3개를 지나야 했다.
> 점검 결과 같은 문제가 네 카테고리에 전부 있었다.
> v8에서 한 번 더 걸렸다. 서론만 줄이고 잘라낸 내용을 바로 뒤에 옮겨
> 분량이 그대로였다. 그래서 법칙 4(소제목 판정)를 추가했다.

---

## 1. 공통 3법칙

### 법칙 1 — 서론은 3~5문장, 한 덩어리로

계기·배경·인사말을 늘리지 않는다. **한 덩어리 안에서 끝낸다.**
서론을 짧게 줄이고 잘라낸 내용을 바로 뒤 텍스트 블록으로 옮기는 것은
규칙만 지키고 문제를 남기는 것이다. 법칙 4로 판정한다.

```
1문장  독자의 상황을 짚는다        "오크라 사놓고 어떻게 먹을지 몰라 시들린 적 있으신가요."
2문장  결론을 먼저 준다            "2분 데쳐서 무치면 되는 15분 반찬이에요."
3문장  이 글의 관문을 예고한다      "어려운 건 물러지지 않게 데치는 것 하나뿐이에요."
4문장  [선택] 이번 건의 조건        "초록 오크라와 붉은 오크라를 섞어서 만들어 봤어요."
```

2문장의 **결론 선제시**가 핵심이다. 공식 가이드가 말하는 "핵심 정보를 쉽고 빠르게"에 대응한다.

### 법칙 1.5 — 독자를 한 장면으로 세우고, 그 사람의 질문 순서로 배열한다

글을 쓰기 전에 **독자가 처한 장면 하나**를 정한다. 공식 체크가이드 1번이 요구하는 것이다.

> "누가, 언제, 어떤 상황(TPO)에서, 어떤 목적으로 이 정보를 찾게 될지
> 독자의 관점에서 콘텐츠를 작성하셨나요?"

그다음 **그 사람이 묻는 순서대로** 소제목을 배열한다.
검색어 순위나 자료의 목차 순서가 아니다.

```
장면   시장에서 못 보던 사과를 봤다. 사장님이 '홍로'라고 한다. 처음 듣는다.
목적   지금 살지 말지 정해야 한다.

질문 순서
  1. 무슨 맛이야?        ← 살지 말지
  2. 지금이 철이야?      ← 사도 되나
  3. 얼마나 두고 먹어?   ← 몇 kg 살까
  4. 어떤 걸 골라?       ← 고르는 중
  5. 이게 뭔 사과야?     ← 사고 나서
  6. 왜 처음 봤지?       ← 배경
```

**결정에 필요한 정보가 앞, 배경과 역사는 뒤다.**

> **오류 기록** — 홍로 초안 v1~v3은 `수확시기 → 품종 유래 → 맛 → 색 → 보관` 순이었다.
> 자동완성 상위 질의를 앞에 놓고 자료의 목차를 따라간 결과다.
> 정작 시장에서 처음 본 사람이 가장 먼저 묻는 **"무슨 맛이야"** 가 세 번째에 있었다.
> **검색어 순위와 독자의 질문 순서는 다르다.** 앞자리 검색어는 유입을 만들고,
> 배열은 이탈을 막는다. 둘을 같은 것으로 쓰면 안 된다.

### 법칙 2 — 핵심 정보 블록을 앞에

각 카테고리마다 **독자가 검색해서 들어온 이유**에 해당하는 블록이 있다.
그 블록은 **서론과 대표 이미지 바로 다음**에 온다. 배경 설명 뒤로 미루지 않는다.

| 카테고리 | 핵심 정보 블록 | 들어갈 것 |
|---|---|---|
| 레시피 | `재료준비` | 조리시간·인분·재료·계량 |
| 내돈내산(장소) | `정보블록` | 위치·영업시간·주차·가격대·대표메뉴 |
| 내돈내산(물건) | `제품 정보` | 제품명·가격·구입처·사용 기간 |
| 체험단 | `제품 정보` | 제품명·구성·규격·가격 (**대가성 고지가 그 위**) |
| 정보성 | `핵심 답 요약` | 제목이 던진 질문에 대한 3~5줄 결론 |
| 운동(일지) | `이번 회차 요약` | 기간·횟수·정량 변화 |
| 운동(수업) | `수업 정보` | 요일·시간·장소·정원·가격·문의처 |
| 운동(워크샵) | `워크샵 정보` | 일시·장소·비용·준비물 |

이 블록은 `quotation` 컴포넌트로 넣는다. 시각적으로 분리되고, 인용 단위로도 잘린다.

### 법칙 3 — 해석·배경·효능은 뒤로

재료의 유래, 성분표 비교, 브랜드 이야기, 개인적 감상은 **본문을 다 읽은 뒤**에 온다.
읽고 싶은 사람만 읽으면 되는 내용이다. 앞에 두면 정작 찾아온 정보를 가린다.

예외: **그 정보 없이는 다음 단계를 이해할 수 없을 때**만 앞에 둔다.
(예: 낯선 식재료의 정체를 2~3문장으로 짚는 것)

### 법칙 4 — 소제목 없이 설 수 있는 블록은 셋뿐

```
서론 · 클로징 · 번호 매긴 절차 단계
```

그 외 모든 본문 텍스트는 **소제목 아래**에 있어야 한다.

이 법칙은 법칙 1의 판정 도구이기도 하다.
**서론에 소제목을 붙이고 싶어진다면, 그건 서론이 아니라 본문 섹션이다.**
소제목이 필요하다는 감각은 "이 덩어리가 독립된 주제를 다루고 있다"는 신호다.
서론은 독립된 주제가 아니라 글로 들어가는 문이므로 소제목이 필요 없다.

읽기 편의만의 문제가 아니다. **소제목이 없으면 AI가 잘라 갈 손잡이가 없다.**
소제목 없는 본문 덩어리는 사실상 인용 대상에서 빠진다.

> **실제 사례** — 레시피 v8에서 서론을 3문장으로 줄인 뒤, 잘라낸 내용을
> 대표 이미지 뒤에 소제목 없는 텍스트 블록으로 붙였다. 규칙은 지켰지만
> 독자가 읽어야 할 분량은 그대로였고, 문제는 하나도 해결되지 않았다.
> 그 블록에 소제목을 붙일 수 있는지 물었더니 답이 나왔다.
> `오크라는 어떤 채소인가요?` 라는 소제목이 붙는 순간 그것은 섹션이 되었고,
> 조리에 필수가 아니므로 글 뒤로 갔다.

**서론에 남길지 뒤로 보낼지 가르는 질문**

```
이 내용 없이도 독자가 다음 단계를 할 수 있는가?
  예 → 뒤로 (소제목을 달아 섹션으로)
  아니오 → 서론에 한 문장으로
```

레시피 v9 적용 예:

| 내용 | 없어도 되나 | 결과 |
|---|---|---|
| 아욱과 아열대 채소, 7~9월 제철 | 예 | 뒤 FAQ `오크라는 어떤 채소인가요?` |
| 점액은 수용성 식이섬유 | 예 | 같은 FAQ로 |
| 초록·붉은 섞어서 만든다 | **아니오** — 이번 재료의 조건 | 서론에 한 문장 |

### 법칙 5 — 사진이 먼저, 설명이 다음

사진과 그 사진을 설명하는 텍스트가 짝을 이룰 때는 **사진을 앞에 둔다.**

```
○  [사진]  꼭지를 잘라낸 모습
   [본문]  데친 뒤에 자르세요. …

✕  [본문]  데친 뒤에 자르세요. …
   [사진]  꼭지를 잘라낸 모습
```

사진을 먼저 보고 "이게 뭐지" 하는 상태에서 설명을 읽는 것이 자연스럽다.
설명을 먼저 읽으면 사진은 확인용으로만 남는다.

질문형 소제목이 붙는 구간도 같다. **소제목 → 사진 → 답** 순서다.
답은 사진 다음 첫 텍스트의 첫 줄에 온다
(`docs/title-heading-spec.md` §2 원칙 2).

예외는 **완성 선언**처럼 텍스트가 사진의 설명이 아니라 독립된 선언일 때인데,
이 경우도 사진을 먼저 두는 편이 읽기 자연스러워 사진 → 선언으로 통일한다.

### 법칙 6 — 구분선으로 섹션을 끊는다

발행본 실측 결과 구분선(`horizontalLine`)을 **11개** 썼다. 초안은 3개였다.

```
[HR]
[quotation]   질문형 소제목
[image]
[text]        답
[text]        절차
[HR]
[quotation]   다음 소제목
...
[quotation]   후기 & 팁
[image]
[text]        팁 1
[HR]
[text]        팁 2
[HR]
[text]        팁 3
[HR]
```

**소제목 블록 앞, 팁 항목 사이, 데이터 블록 위아래**에 넣는다.
과거 글의 사용량은 1~9개로 편차가 크지만 최근으로 올수록 늘어난다.
**섹션당 1개**를 기준으로 삼는다.

### 법칙 7 — 빈 텍스트 블록으로 여백을 만든다

내용 없는 `text` 컴포넌트를 넣어 간격을 준다. 재료준비 블록 앞뒤 등.
과거 9편 중앙값 2개, 발행본 3개. 붙여넣기 원고에는 `[빈 줄]` 로 표기한다.

### 법칙 8 — 같은 단계의 사진 2장은 imageGroup으로

발행본에서 된장·참기름 두 장을 `imageGroup` 으로 묶었다.
붙여넣기 원고에 `사진 9, 10 (묶어서)` 로 표기한다.

## 2. 표준 시퀀스

```
①  서명 라인          text          {수식} {대상명} {레시피|만드는법}_by{징키|링키}
②  훅 소제목          sectionTitle  2개(2줄). **①과 다른 각도의 후킹 문구**
③  구분선
④  서론               text          3문장. 결론 선제시 포함
⑤  대표 이미지        image         첫 이미지 = 썸네일. 결과물 컷을 쓴다
⑥  [최소 배경]        text          2~3문장. 없으면 생략
⑦  핵심 정보 블록 ★  quotation     법칙 2 표 참조
⑧  본문 섹션          ── 반복 ─────────────────────
                      [horizontalLine]
                      quotation     질문형 소제목
                      image         1~3장          ← 사진이 먼저
                      text          3~7줄. 첫 줄이 답
                      ────────────────────────────
⑨  결과·완성 선언     image + text
⑩  후기 & 팁 ★       quotation     직접 겪은 것만
⑪  [심화 FAQ]         quotation     해석·배경·효능·성분. 출처 병기
⑫  클로징             text          3~4줄
```

★ 두 블록은 **모든 카테고리 필수**다. 누락 시 생성 차단.

⑤ 대표 이미지는 **결과물**을 쓴다. 완성된 요리, 방문한 공간의 전경, 제품 개봉 후 모습.
재료·부품·포장 상태를 첫 이미지로 쓰면 썸네일에서 무슨 글인지 알 수 없다.

### 서명 라인과 훅 소제목은 서로 다른 문구다

**서명은 대상을 지칭하고, 훅은 다른 각도로 후킹한다.** 레시피 9편 실측:

| 서명 라인 (`text`) | 훅 소제목 (`sectionTitle` 2개) |
|---|---|
| 저속노화 건강반찬 양배추샐러드_by링키 | 영양과 드레싱이 기가막힌 / 양배추샐러드 |
| 가지구이무침 양념 레시피_by장키 | 가지구이 한다면 / 이 레시피 꼭 챙기세요 |
| 임짱 임성근셰프 무조림 직접해 봄_by링키 | 집에서 남대문 갈치조림맛을 낼 수 있다면? |
| 마녀스프 대용, 토달볶 활용법_by링키 | 재료 오직 3가지! / 무수분 토마토 스프 요리 |

**훅 컴포넌트는 `sectionTitle` 이다. `quotation` 이 아니다** (9편 중 7편).
`quotation` 은 본문 소제목과 재료준비·후기팁 블록에 쓴다.

> **오류 기록** — v11에서 서명과 훅을 "같은 말"로 보고 중복 판정했고,
> 작성자가 톤앤매너를 지적하자 v14에서 "같은 문구가 하우스 패턴"이라며 되돌렸다.
> **양쪽 다 틀렸다.** 둘은 서로 다른 문구이되, 서명은 일기체가 아니라 요리 지칭이어야 한다.
> 지적의 내용(톤)을 다른 문제(중복)로 잘못 읽고 규칙을 두 번 뒤집었다.
>
> 중복 검사는 **본문끼리**에만 적용한다.

## 3. 카테고리별 점검 결과와 수정

### 레시피 — 수정 완료

| 문제 | 수정 |
|---|---|
| 도입 4문단 | 4문장 한 덩어리로 |
| 서론에서 잘라낸 배경을 소제목 없이 뒤에 붙임 (v8) | 소제목 달아 글 뒤 FAQ로 (v9) |
| `재료준비`가 12번째 덩어리 | 3번째로 이동 |
| 정보 Q&A 3개가 재료 앞 | 성분 비교는 후기·팁 뒤로, 재료 소개만 2~3문장 남김 |
| 대표 이미지가 재료 컷 | 완성컷으로 교체 |
| 레드/그린 비교가 앞에 따로 | 데치기 단계 옆으로 이동 (중복 제거) |

### 내돈내산 — 수정 필요

| 문제 | 수정 |
|---|---|
| 도입 3~5줄 | 3문장 |
| 정보블록에 **가격대·대표메뉴가 없다** | 두 항목 추가. 검색 의도의 핵심이다 |
| 지도가 정보블록보다 앞 | 정보블록 → 지도 순서로. 텍스트가 먼저 인용된다 |
| 웨이팅·주차를 제목에 나열 | 제목에서 빼고 **질문형 소제목**으로 (`주차는 어디에 하나요?`) |

### 체험단 — 수정 필요

| 문제 | 수정 |
|---|---|
| **제품 정보 블록이 아예 없다** | 신설. 제품명·구성·규격·가격 |
| 대가성 고지가 배너 이미지에만 의존 | 텍스트 고지를 **서명 라인 바로 위**에 병기 |
| `추천 대상`·구매 링크가 맨 뒤 | 위치는 유지. 다만 본문이 정보 없이 홍보뿐이면 감점 대상 |

### 정보성 — 수정 필요 (가장 중요)

| 문제 | 수정 |
|---|---|
| **제목의 질문에 대한 답이 도입에 없다** | `핵심 답 요약` 블록 신설. 대표 이미지 직후 |
| 도입이 "문제 제기 + 답할 것 예고" | 예고가 아니라 **답을 준다**. 상세는 본문에서 |

정보성은 이 문제가 구조적이다. 답을 뒤로 미루는 구성이 곧 낚시 구조이고,
`docs/title-heading-spec.md` 에서 폐기한 후킹 어구 사전이 그 구성을 전제하고 있었다.
**제목이 질문이면 첫 화면에 답이 있어야 한다.** AI 브리핑 인용에도 이쪽이 압도적으로 유리하다.

```
제목   오크라 데치면 영양이 줄까요, 성분표로 비교했습니다
       ↓
핵심 답 요약 (대표 이미지 직후)
       비타민 C는 줄고, 식이섬유는 줄지 않습니다.
       100g 기준 비타민 C 11mg → 7mg,
       총 식이섬유 5g → 5.2g 입니다.
       (농촌진흥청 국가표준식품성분표 기준)
       ↓
본문   왜 그런지, 어떻게 확인했는지
```

### 운동 — 수정 필요

| 유형 | 문제 | 수정 |
|---|---|---|
| 수련 일지 | **10일치 나열만 있고 요약이 없다** | `이번 회차 요약` 블록 신설. 기간·횟수·정량 변화 |
| 수련 일지 | `기록 방식 안내`가 매 편 반복되는 상용구 | 클로징 직전으로 이동 또는 생략 |
| 수업 안내 | 가격·시간·장소가 본문에 흩어져 있다 | `수업 정보` 블록으로 묶어 앞에 |
| 워크샵 후기 | 일시·장소·비용이 없는 편이 있다 | `워크샵 정보` 블록 신설 |

수련 일지의 `이번 회차 요약`은 `docs/style-profile-training.md` §2.6의 정량 지표와 연결된다.
독자가 "31~40일 동안 뭐가 달라졌나"를 첫 화면에서 알 수 있어야 한다.

## 4. 각도가 구조를 정한다

`docs/title-heading-spec.md` §5의 각도 결정이 문서 구조에도 영향을 준다.
**같은 경험이라도 각도가 다르면 핵심 정보 블록이 달라진다.**

| 각도 | 핵심 정보 블록 | 앞에 와야 할 것 |
|---|---|---|
| `{요리명} 만드는법` | 재료준비 | 재료·계량·조리시간 |
| `{재료} 데치는법` | 데치기 조건 | 물·시간·판정법 |
| `{재료} 먹는법` | 활용 목록 | 이 재료로 할 수 있는 것 |
| `{재료} 효능` | 핵심 답 요약 | 결론 + 근거 수치 + 출처 |

각도를 정했으면 그 각도의 핵심 정보가 다섯 번째 덩어리 안에 있어야 한다.

> **오크라 v10 자가 점검** — 각도는 `오크라 데치는법` 인데 구조는 레시피 그대로다.
> 재료준비가 여덟 번째, 데치기 조건은 열두 번째에 있다.
> 다만 제목·훅·서론·소제목·팁 1~3이 전부 데치기를 다루고 있어
> 질의에 대한 답 자체는 충분히 앞에 노출된다. 이번 편은 이대로 둔다.
> **다음 편부터는 각도를 먼저 정하고 구조를 짠다.**

## 5. 발행 전 점검 (6항목)

```
[ ] 독자의 장면(TPO)을 한 문장으로 말할 수 있다
[ ] 소제목 순서가 그 사람의 질문 순서와 같다
[ ] 서론이 5문장 이내이고 한 덩어리다
[ ] 서론 안에 결론이 한 번 나온다
[ ] 대표 이미지가 결과물 컷이다
[ ] 핵심 정보 블록이 다섯 번째 덩어리 안에 있다
[ ] 해석·배경·효능이 본문 뒤에 있다
[ ] 같은 설명이 두 곳에 중복되지 않는다
[ ] 소제목 없는 텍스트 블록이 서론·클로징·절차 단계 외에 없다
[ ] 정한 각도의 핵심 정보가 다섯 번째 덩어리 안에 있다
[ ] 후기·팁이 본문 문장을 그대로 옮기지 않았다
[ ] 사진과 설명이 짝일 때 사진이 앞에 있다
[ ] 구분선이 섹션당 1개 있다
[ ] 훅은 sectionTitle, 소제목은 quotation으로 지정했다
[ ] 확인되지 않은 내용이 남아 있지 않다
[ ] **제목을 바꿨다면 서명 라인·훅 소제목·서론을 함께 확인했다**
```

### 제목이 바뀌면 서명·훅·서론이 따라와야 한다

제목은 각도가 바뀔 때마다 여러 번 고쳐진다. 그때 **서명 라인·훅 소제목·서론**은
그대로 남기 쉽다. 이 셋은 앞자리에 있으면서 뒤쪽 내용을 요약하는 자리라
수정 누락이 눈에 잘 띄지 않는다.

```
제목    홍로사과 왜 추석마다 나올까요? 9월 수확기가 답이에요   ← v10에서 바꿈
서명    처음 본 사과 홍로_by징키                            ← v4 그대로
훅      시장에서 만난 / 낯선 사과, 홍로                      ← v4 그대로
```

글이 두 방향을 가리킨다. **제목을 고치는 커밋에서 이 셋을 함께 본다.**

> **오류 기록 (2회)** — 오크라 v7에서 같은 문제를 겪고 이 점검을 만들었는데,
> 홍로 v10에서 다시 놓쳤다. 작성자가 발견했다.
> 만들어 둔 점검을 실행하지 않은 것이므로, 점검 목록에 항목으로 못박는다.
>
> 참고: **서명·훅은 검색 대상이 아니다.** 검색되는 것은 제목뿐이므로
> 검색어일 필요가 없다. 문제는 검색이 아니라 **방향 일치**다.

### 후기·팁 블록은 요약이 아니라 압축과 보강이다

본문 문장을 그대로 옮기면 인용 가치가 없고 분량만 는다.
팁에는 **본문에 없는 각도**가 있어야 한다. 왜 그런지, 무엇과 혼동하기 쉬운지,
안 하면 어떻게 되는지, 다른 방법은 없는지.

### 규격 문서의 라벨을 본문에 넣지 않는다

규격에 `핵심 답`, `제품 정보`, `이번 회차 요약` 같은 블록 이름이 나오는데,
이는 **"이 자리에 이런 블록이 온다"는 표시**이지 독자가 읽을 문구가 아니다.

| 본문에 쓰는 라벨 | 근거 |
|---|---|
| `재료준비` | 레시피 과거 글 9/9에 실제로 있다 |
| `{요리명} 레시피 후기 & 팁` | 같음 |
| `제품정보` | 체험단에 신설. 실제 라벨로 쓰기로 결정한 것 |

| 본문에 쓰지 않는 라벨 | 이유 |
|---|---|
| `핵심 답` | 규격 설명용 이름. 과거 글에 없다 |
| `이번 회차 요약` | 같음. 실제로는 `31-40일차 요약` 처럼 구체화한다 |

**과거 글에 실제로 등장하는 라벨만 본문에 쓴다.** 나머지는 그 자리에 맞는
질문형 소제목이나 구체적 제목으로 바꾼다.

### 확인되지 않은 내용에 표시를 붙여 남기지 않는다

`※ 확인 필요` 를 붙이는 것은 지어낸 정보를 남길 근거가 되지 않는다.
확인되지 않으면 **삭제한다.** 작성자가 채우면 그때 넣는다.
표시를 붙여 두면 발행 시 그대로 나갈 위험이 있고, 실제로 두 번 그럴 뻔했다.

네 번째 항목은 기계적으로 검사할 수 있다. **컴포넌트 인덱스로 세면 된다.**
