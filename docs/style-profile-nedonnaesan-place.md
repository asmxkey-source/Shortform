# 스타일 프로파일 — 내돈내산 장소형 (카페·식당 통합)

> **이 절은 `docs/document-structure-spec.md` 와 `docs/title-heading-spec.md` 를 상속한다.**
> 공통 법칙(서론 3~5문장 / 핵심 정보 블록을 앞에 / 행동 동선으로 배열 / 사진 먼저 /
> 구분선 · 라벨 · 메타 서술 규칙)은 그 문서들에 있다. 여기에는 **장소 방문 리뷰 고유 사항**만 담는다.
>
> **근거**: 작성자가 2026-09-02 제공한 "외식 리뷰" 작성 양식(네이버 블로그 앱 스크린샷 7장).
> 기존 `docs/style-profile-nedonnaesan-cafe.md`(물루 카페 1편 분석)를 이 문서로 **대체**한다.
> 그 문서의 유효한 결함 발견(시간 표기·상호 표기 일관성)은 §8에 옮겨 왔다.
>
> **카페와 식당을 하나로 묶는 이유**: 구조가 같다. 정보블록 → 분위기 → 메뉴판·가격 →
> 주문메뉴 → 메뉴별 리뷰 → (조건부) 웨이팅 → 총평. 다른 것은 목표 카테고리와 제목 프레이밍 두 곳뿐이다.

## 0. 카테고리 분기 — 이 문서 안의 유일한 갈림길

`docs/naver-category-map.md` §4.1 기준.

| 방문 장소 | 네이버 카테고리 | 제목 프레이밍 |
|---|---|---|
| 카페·베이커리·디저트 | **간식 리뷰** | 용도(작업·조용함·데이트·공부) |
| 식당·술집 | **외식 리뷰** | 맛집·회식·가족모임·혼밥 |

나머지 구조·규칙은 완전히 같다. 이하 "가게"는 카페·식당 공통 지칭이다.

## 1. 입력 규격 — 경험 게이트

내돈내산 장소형이므로 경험 게이트가 걸린다. 작성자에게 받는 것:

| # | 항목 | 필수 |
|---|---|---|
| 1 | 가게 이름·주소 (또는 네이버 플레이스 링크) | 필수 |
| 2 | 방문 계기 한 줄 | 필수 |
| 3 | 주문한 메뉴명·가격 + **누가 주문했나** (징키/링키/함께) | 필수 |
| 4 | 메뉴별 식감·간·양 인상 (직접 겪은 것) | 필수 |
| 5 | 대기 시간·직원 응대 | 대기가 있었을 때만 |
| 6 | 장단점 1~2개씩, 재방문 의사 | 필수 |
| 7 | 사진 | 있을수록 좋음. 없어도 진행 가능 |

**2·4·6번이 경험 게이트의 핵심이다.** 이게 없으면 정보성처럼 자료를 옮기는 글이 되고,
내돈내산 카테고리는 출처 게이트가 없으므로 아예 쓸 근거가 없다.

### 자동 조회 예정 (M2+, 아직 미구현)

**● 예약 및 평점** 항목의 평점·리뷰 수는 네이버 플레이스 원본 값이다.
지금은 **작성자가 방문 전후 직접 확인해 입력**한다. 발행용 세션이 확보되는 M2 이후,
플레이스 페이지에서 자동 조회하는 기능을 넣는다. PRD FR 항목 참조.

## 2. 문서 골격

```
①  서명 라인        text          {방문지 요약}_by{징키|링키}
②  훅 소제목        sectionTitle  2줄. ①과 다른 각도의 후킹 문구
③  구분선
④  서론             text          3~5문장. 방문 계기 + 결론 선제시
⑤  대표 이미지      image         외관 또는 결과물 컷 (썸네일)
⑥  정보블록 ★      quotation     "{가게명} 위치 및 주차 정보" + 지도
                    map
                    text          ● 위치 / ● 운영시간 / ● 주차
                                  / ● 예약 및 평점 / ● 그 외 사항
⑦  분위기           quotation     "{가게명} 매장 분위기"
                    text          질문형 도입 ("내부 분위기는 어떨까요?")
                    image         외관 → 내부 순
⑧  메뉴판·가격      quotation     "{가게명} 메뉴판과 가격"
                    text          질문형 도입 ("가격대는 어느 정도일까요?")
                    image         메뉴판 사진
                    text          대표 메뉴 3~5개 가격
⑨  주문메뉴 ★      quotation     "주문 메뉴, 맛은 어땠을까?"
                    quotation     "{징키|링키} 주문메뉴" + 항목·가격 나열
⑩  메뉴별 리뷰      ── 메뉴 수만큼 반복 ─────────────
                    image         메뉴 사진 (사진이 먼저)
                    text          식감·간·양 등 직접 겪은 것 3~4줄
                    ─────────────────────────────
⑪  [웨이팅과 서비스] quotation     대기가 있었을 때만. 조건부 섹션
                    text          대기 시간·예약 가능 여부·직원 응대
⑫  총평             quotation     "{가게명} 총평, 이런 분께 추천해요"
                    text          장단점 1~2개씩 + 재방문 의사 + 추천 대상
⑬  고정 배너        image         "푸드 전문블로거 @{징키|링키}" (자산 필요, §7 참조)
```

★ 두 블록은 필수. 누락 시 생성 차단.

### 조건부 섹션 — ⑪이 이 규격의 첫 사례

**대기가 없었으면 섹션 전체를 뺀다.** 있었을 때만 넣는다.
이 문서 전체에서 조건부 섹션의 첫 사례이며, 판단 기준은 다음과 같다.

```
조건부 섹션 판단   그 경험이 실제로 있었는가?
                  없으면 섹션째로 뺀다. "웨이팅 없었어요" 한 줄로 때우지 않는다.
```

다른 카테고리에도 같은 패턴이 적용될 수 있다 (예: 레시피의 실패 재시도 경험,
운동 워크샵의 부상·중단 경험). 발생하면 이 절을 참조해 조건부 섹션으로 처리한다.

## 3. 정보블록 — 필드 확장

기존 §정보블록(내돈내산 공통, `style-profile-nedonnaesan.md` §5)에 두 필드를 추가한다.

```
● 위치      {역명} {번}번 출구에서 {거리}m (도보 {n}분)
            여러 역에서 접근 가능하면 출구별로 각각 적는다.
● 영업시간  {요일 범위} {시작}~{종료} (브레이크타임 {시작}~{종료})
            · 라스트오더 {영업종료 몇 분 전}
            · 전화번호
● 주차      가능/불가·조건
● 예약 및 평점   신설
            · 예약 채널 (캐치테이블·네이버예약·전화 등)
            · 평점 {n}점 / 리뷰 {n}개 이상 (플레이스 원본 값. §1 자동조회 예정)
● 그 외 사항   1인 주문 가능 여부·화장실 분리 등 실용 정보
```

**여러 지하철역에서 접근 가능하면 출구별로 경로를 병기한다.** 하나의 역만 가깝다면
그 하나만 적는다. 강제로 2개를 채우지 않는다.

### 가격 표기 (기존 규칙 유지)

- `11,000원` 형식. 천단위 콤마 + 원
- 단위당 환산 병기 시 GEO에 유리: `6칩에 33,000원 (잔당 5,500원)`

## 4. 주문메뉴 블록 — 레시피 `재료준비`에 대응하는 자산

```
{징키|링키|링키징키} 주문메뉴
{메뉴1} {가격}
{메뉴2} {가격}
```

**실제로 주문한 것만 적는다.** 메뉴판 전체를 옮기지 않는다.
레시피의 `재료준비`처럼 **그 자체로 완결된 구조화 데이터**라 인용 단위가 된다.
"OOO 주문메뉴", "OOO 가격" 같은 질의에 통째로 인용될 수 있다.

### 이름 값은 발행 작성자가 아니라 실제 주문자를 따른다

`징키` · `링키` · `링키징키` 셋 다 실제로 쓰이는 값이다. **누가 주문했는지**로 정하며,
서명 라인·훅처럼 발행 작성자 한 명을 그대로 따르는 필드가 아니다.

```
혼자 방문해서 혼자 주문   징키 주문메뉴   또는   링키 주문메뉴
둘이 방문해서 나눠 주문   링키징키 주문메뉴
```

발행 작성자(서명 라인의 `_by징키`)와 주문메뉴의 이름이 **다를 수 있다.**
예: 링키가 쓴 글인데 그날은 둘이 같이 갔으면 `링키징키 주문메뉴`가 맞다.
작성 시 "누가 주문했나요?"를 별도로 물어야 하는 이유다.

## 5. 메뉴별 리뷰 — 식감·간·양 3축 고정

```
[image]  메뉴 사진   ← 사진이 먼저 (법칙 5)
[text]   식감: {씹는 느낌·질감}
         간: {짜기·삼삼함·간이 밴 정도}
         양: {1인분 기준 충분한지}
```

세 축을 문항처럼 나열하지 않고 **자연스러운 3~4줄 서술**로 녹인다. 예:

```
겉은 바삭하고 속은 촉촉했어요.
간은 삼삼한 편이라 아이도 먹기 좋았고,
양은 둘이 나눠 먹기에 딱 맞았어요.
```

**세 축 중 하나라도 빠지면 생성 차단.** 이게 이 카테고리의 "창작자만 아는 팁"에 해당하는
자리이고, 메뉴판 정보와 차별화되는 유일한 경험 서술이다.

## 6. 총평 — 3요소 고정

```
{가게명} 총평, 이런 분께 추천해요

장점: {1~2개}
아쉬운 점: {1~2개}
재방문 의사: {있다/없다 + 이유 한 줄}
추천 대상: {어떤 상황·어떤 사람에게}
```

**아쉬운 점이 반드시 포함된다.** 체험단 프로파일의 "아쉬운 점 최소 1개" 규칙과 같은 이유다.
공식 가이드가 "본문이 정보 없이 홍보성 멘트로만 가득하면 가치가 낮다"고 명시한다.

## 7. 남은 자산 — 준비되지 않은 것

체험단의 "자체 고지 배너"와 같은 유형이다. 실물이 있어야 진행된다.

| 자산 | 상태 |
|---|---|
| 마무리 고정 배너 ("푸드 전문블로거 @징키/@링키") | 디자인 확인됨 (§7.1). **원본 파일 확보 대기** |
| 평점·리뷰 자동 조회 | M2 이후. 지금은 작성자 수기 입력 |

### 7.1 고정 배너 — 디자인 확인 (2026-09-06)

작성자가 실물 이미지를 보여줬으나 이 세션에서 파일로 받지 못해 원본은 아직 없다.
디자인만 텍스트로 기록해 둔다.

```
레이아웃   좌우 2분할
좌측       주황색 단호박 + 호박 캐릭터, 둘 다 눈알 스티커(움직이는 눈) 부착
우측       그라데이션 배경(핑크 → 오렌지)
           "푸드 전문블로거" (흰 텍스트, 작게)
           네이버 로고 "N" | "@링키징키" 를 흰 테두리 박스 안에
           "네이버에서 검색하고 🙂 팬하기" (하단, 작게)
용도       모든 장소형(카페·식당) 글의 마지막 컴포넌트. 고정 재사용
```

`@링키징키`로 고정돼 있다. §4에서 정리한 "주문메뉴 이름은 실제 주문자를 따른다"와는
**다른 필드다.** 이 배너의 계정 표기는 방문자 구성과 무관하게 **블로그 공식 배지로 고정**이다.

> **파일 확보 방법** — 이미지를 다시 첨부(붙여넣기 아님)하면 로컬 파일로 받아
> `data/raw/source/` 또는 애셋 디렉터리에 저장하고 이 표를 갱신한다.

## 8. 물루 카페 분석에서 이월한 결함 (여전히 유효)

구 `nedonnaesan-cafe.md`에서 발견된 것 중 이 문서에도 적용되는 것.

- **상호 표기 흔들림** — 같은 글 안에서 `물루`/`몰루`처럼 표기가 흔들렸다.
  생성 후 **고유명사 일관성 검사**가 필요하다 (본문 전체에서 상호명 표기가 1종인지).
- **시간 표기 불일치** — `09:00~19:00`(물결)과 `11:00-19:00`(하이픈)이 섞였다.
  **물결(`~`)로 정규화**한다.
- **지역 키워드 확장 시 본문과 충돌 금지** — 태그에 인접 지역을 추가로 넣을 수 있으나
  본문·제목이 말하는 지역과 모순되면 안 된다 ("무관한 키워드 삽입" 위반).

## 9. 어투 (기존 카페 분석 유지 — 검증 시까지 잠정)

물루 카페 1편에서 실측한 값이다. 표본이 늘면 갱신한다.

| 지표 | 값 |
|---|---|
| 종결어미 | 해요체 7할 + 합니다체 3할 |
| 줄 길이 | 평균 13.9자 |
| 이모지 | 0 |
| 볼드·색 강조 | 주의사항 최대 5회, `#0095e9` |
| 정렬 | 가운데 정렬 다수 |

**추측·완충 표현**을 쓴다 — "좋았던", "~것 같았어요", "~해 보였어요".
단정 대신 관찰자 시점. 과장 감탄사("존맛" 류)는 쓰지 않는다.

## 10. 생성 프롬프트용 요약 스펙

```yaml
category_branch:
  카페·베이커리·디저트: 간식 리뷰
  식당·술집: 외식 리뷰
input_gate: experience               # 경험 게이트. 출처 게이트 아님
required_inputs: [가게명·주소, 방문계기, 주문메뉴·가격, 메뉴별식감간양, 장단점, 재방문의사]
optional_inputs: [사진, 대기시간·응대]
structure:
  order: [서명, 훅, 서론, 대표이미지, 정보블록, 분위기, 메뉴판가격,
          주문메뉴, 메뉴별리뷰xN, 웨이팅?, 총평, 고정배너]
required_blocks:
  정보블록:
    fields: [위치, 영업시간, 주차, 예약및평점, 그외사항]
    위치_형식: "{역명} {번}번 출구에서 {거리}m"
    시간_형식: "물결(~) 로 정규화"
  주문메뉴:
    component: quotation
    label: "{징키|링키|링키징키} 주문메뉴"    # 발행 작성자가 아니라 실제 주문자
    format: "{메뉴} {가격,원}"
```

## 11. 확정 사항 / 남은 것

**확정**
- 카페·식당 통합 문서로 운영한다. 카테고리 분기만 §0에서 처리한다.
- `주문메뉴` · `메뉴별 식감·간·양` 두 블록은 필수. 누락 시 생성 차단.
- 주문메뉴의 이름 값(징키/링키/링키징키)은 발행 작성자가 아니라 **실제 주문자**를 따른다.
  작성 시 "누가 주문했나요?"를 별도로 묻는다.
- 총평에 아쉬운 점을 반드시 포함한다.
- 웨이팅 섹션은 조건부 — 있었을 때만 넣는다. 이 규격의 첫 조건부 섹션 사례다.

**남은 것**
- 마무리 고정 배너 원본 파일 확보 (디자인은 §7.1에 확인·기록됨).
- 평점·리뷰 자동 조회 기능은 M2 이후 구현.
- 카페 어투(§9)는 표본 1편 기준. 식당 표본이 쌓이면 갱신.
